# Pier 安全设计：远程访问、配对与加密通道

> 实现：`packages/crypto`（Noise、通道帧、配对链接、多路径会话、中继协议）、`packages/host/src/remote/`（监听、中继注册、P2P、配对、设备登记、审计）、`packages/client/src/secure.ts` 与 `p2p.ts`（设备端）、`apps/relay`（中继服务器）。
> 适用范围：局域网 / Tailscale 直连，以及经 Pier Relay 的连接与在其上建立的 P2P 路径（§5）。三种路径使用同一套端到端加密。

## 1. 威胁模型

- **Host 等同于这台电脑的远程执行入口。** 任何能与 Host 建立已认证连接的设备，都能让 Agent 在电脑上读写文件、运行命令（仍受工作区审批策略约束）。
- **网络不可信。** 包括家里 / 公司的局域网、公共 Wi‑Fi、Tailscale 网络和中继服务器：攻击者可能监听、篡改、重放或伪造任意帧，也可能主动连接 Host 的端口。中继的运营者同样不被信任。
- **需要保护的内容：** 会话内容（代码、命令、输出）、工具调用与审批决定、Host 的执行能力本身。
- **不在范围内：** 已被攻破的电脑或手机本身（能读取私钥或 `~/.pier`）、针对可用性的攻击（例如在局域网内阻断连接、耗尽端口）、pi 本身的模型与凭据安全。

## 2. 密钥

| 密钥 | 类型 | 存放位置 | 用途 |
|---|---|---|---|
| Host 静态密钥 | X25519 | `~/.pier/identity.json`（0600，Host 首次启动时生成） | 手机在配对时固定（pin）它的公钥，之后每次连接都据此认证 Host；连接其他电脑时也用作这台电脑的设备密钥（§4.4） |
| 设备静态密钥 | X25519 | 手机的 Keychain / Keystore（`expo-secure-store`，`AFTER_FIRST_UNLOCK_THIS_DEVICE_ONLY`，不随备份迁移） | Host 按公钥识别设备 |
| 临时密钥 | X25519 | 内存，每次握手新生成 | 前向保密 |
| 本地 token | 32 字节随机数 | 仅内存与 `run/host.json`（0600） | 桌面 WebView 连接 `127.0.0.1`（不经过本文的加密通道） |

指纹：公钥 SHA‑256 的前 10 字节，按 Base32 每 4 个字符分组（如 `K7QF-2M4A-XJ3D-9PLR`）。桌面在配对确认框和设备列表中显示设备指纹，手机在等待确认时显示自己的指纹，可当面核对；桌面设置页也显示 Host 指纹。

## 3. 连接与暴露面

- **远程访问默认关闭。** 在桌面“手机与远程访问”中开启后，Host 在 `0.0.0.0:7433`（可改端口，IPv4 与 IPv6）监听，并通过 mDNS 广播 `_pier._tcp`（TXT 只含 hostId 与协议版本）。关闭后立即断开所有远程连接（关闭码 4410）。
- 监听器只接受 Noise 握手：在握手完成、设备通过认证之前，Host 不解析任何 Pier 协议帧，也不透露除错误码外的任何信息。
- 本地连接（`127.0.0.1` + token + Origin 白名单，见 `docs/protocol.md` §2）与远程监听相互独立；远程设备永远不能调用仅限本地的方法：设备管理、配对、远程访问设置与 `peer.*`，即决定“谁能连接这台电脑”的操作。
- 同时进行中的未认证握手最多 32 个；握手须在 10 秒内完成；每 30 秒 ping 一次，检测已失联的连接。

工作区外文件的单次预览授权从协议 1.35 起对已配对设备开放，与配对即信任的管理权限一致。客户端在用户确认文件所在电脑及实际路径后调用 `workspace.authorizeFilePreview`；Host 重新核对实际路径，只进行一次受大小限制的读取，不保存授权，也不改变工作区文件列表、写入或下载的路径限制。远程调用的审计日志只含工作区与路径，不含文件内容；系统读取权限仍由操作系统执行。

## 4. 加密通道

WebSocket 文本帧，每帧一个 JSON 对象：

```jsonc
{ "t": "hello", "v": 1, "mode": "pair" | "connect", "m": "<base64 Noise 消息 1>" }  // 设备 → Host
{ "t": "hs", "m": "<base64 Noise 消息>" }                                          // 其余握手消息
{ "t": "enc", "n": <nonce>, "c": "<base64 密文>" }                                 // 握手之后的所有帧
{ "t": "error", "code": "UNKNOWN_DEVICE" | ..., "message": "…" }                   // Host 拒绝握手（明文）
```

- 密码套件：**Noise_XX_25519_ChaChaPoly_SHA256**（配对）与 **Noise_IK_25519_ChaChaPoly_SHA256**（之后的连接），Noise 规范第 34 版，使用 `@noble/curves`、`@noble/ciphers`、`@noble/hashes` 的纯 JS 实现（Node、Bun、浏览器与 Hermes 通用）。实现通过了 cacophony 测试向量（`packages/crypto/test/fixtures/noise-vectors.json`）。
- prologue 为 `pier-channel/1 pair` 或 `pier-channel/1 connect`，把模式绑定进握手哈希。
- 握手完成后，`Split()` 得到两个方向各自的 ChaCha20‑Poly1305 密钥。每个 Pier 协议帧加密为一个 `enc` 帧；nonce 是隐式计数器，同时写在 `n` 中，接收方要求 `n` 恰好等于期望值，因此丢帧、重放或乱序都会导致连接关闭。
- **与原始 Noise 的差异：** Noise 传输消息限制为 65535 字节，Pier 的帧可能更大（图片以内联方式发送），所以每个帧整体用 `Split()` 得到的密钥加密，不做分片。ChaCha20‑Poly1305 单条消息的上限远大于 Pier 的 64 MiB 帧上限。每个方向最多 2^53 条消息，超过时连接报错，重连后换新密钥。

### 4.1 配对（Noise XX）

1. 桌面调用 `pairing.start`：Host 生成 16 字节随机的一次性配对码（5 分钟有效），桌面显示二维码：
   `pier://pair?v=1&host=<hostId>&name=<主机名>&pk=<Host 公钥 base64url>&addr=<ip:port,...>&code=<配对码>`
   `addr` 按顺序列出局域网 IPv4 地址（私有网段与 Tailscale 100.64/10 优先；没有 IPv4 时才用 IPv6），最多 4 个；Host 可用 `--remote-address` 指定其他地址。
2. 手机扫码后依次尝试这些地址，发起 XX 握手。收到消息 2 后，**校验 Host 静态公钥与二维码中的 `pk` 完全一致**，不一致立即中止（防中间人）。
3. 消息 3 中，手机发送自己的静态公钥和加密载荷 `{ v, code, device: { name, platform, model, appVersion } }`。
4. Host 以常量时间比较配对码。配对码**只能使用一次**，不论之后是否获准；连续 5 次错误会使当前配对码作废。
5. 配对码正确时，Host 向桌面发出 `pairing.request`（设备名、型号、指纹、来源地址），桌面弹窗询问“允许新设备连接？”。2 分钟内未确认视为超时拒绝。
6. 获准后 Host 把设备公钥登记到 `~/.pier/devices.json`（0600），并通过加密通道回复 `{ ok: true, deviceId, hostId, hostName }`，随后关闭连接。拒绝 / 超时同样以加密结果告知。

手机保存 `hostId`、主机名、Host 公钥、地址列表和 `deviceId`。同一设备密钥再次配对会更新原记录，`deviceId` 不变。

### 4.2 后续连接（Noise IK）

1. 手机已知 Host 公钥，发送 IK 消息 1（含加密的设备静态公钥）。
2. Host 解出设备公钥，**在回复之前**检查它是否已登记。未登记（从未配对或已被吊销）时返回明文 `error { code: "UNKNOWN_DEVICE" }` 并以关闭码 4403 关闭连接；手机据此提示“已被电脑移除，需要重新配对”，不再自动重连。
3. 握手完成后双方互相认证，且有前向保密。之后的流程与本地连接相同：`host.hello`（远程连接不需要 token）、订阅、请求……Host 在 `host.hello` 时再次确认设备仍已登记，结果中带有 `device: { id, name }`。

### 4.3 吊销（手机与电脑相同）

桌面设备列表中“移除”调用 `device.revoke`：设备记录立即删除，该设备的所有连接以关闭码 4403 断开；之后的握手在 4.2 第 2 步被拒绝。手机端“移除这台电脑”只删除手机上的配对信息，不影响 Host；要彻底撤销访问必须在电脑上操作。

### 4.4 电脑之间的连接

每台运行 Pier 的电脑都是一个节点。电脑 A 连接电脑 B 时，A 的 Pier Host **以自己的 Host 静态密钥作为设备密钥**，按 §4.1 / §4.2 与 B 配对和连接，B 把 A 当作普通的远程设备登记（设备名为 A 的主机名，`platform` 为 `darwin` / `linux` / `win32`），因此 B 的设备列表、审计日志与吊销对电脑和手机完全相同。

- **配对**：用户在 B 上生成配对码并复制 `pier://pair?...` 链接，粘贴到 A 的“添加电脑”中；A 的桌面界面调用 `peer.pair`，由 A 的 Host 完成 Noise XX（同样校验 B 的公钥与链接一致）。B 的确认框显示 A 的设备指纹，它与 A 设置页上“这台电脑的密钥指纹”一致，可当面核对。A 在 `~/.pier/peers.json`（0600）中保存 B 的 hostId、主机名、固定的公钥、地址和 deviceId。B 的 IP 变化后，A 的用户可以在「设备与远程」中修改地址（`peer.update`，仅限本机）；公钥仍然固定，改成另一台电脑的地址只会握手失败，不会连到它。
- **连接**：A 的桌面界面不接触任何私钥，而是连接 A 本地 Gateway 的 `/peer/<B 的 hostId>`（仍只监听 `127.0.0.1`，校验 Origin 与本地 token）；A 的 Host 校验 token 后把它从 `host.hello` 中删除，再用 Noise IK 连接 B 并逐帧转发。B 永远看不到 A 的本地 token。
- **权限**：配对即完全信任（协议 1.10）。经代理的连接在 B 上是远程连接，与手机一样可以管理 B：添加 / 移除工作区（用 `host.listDirectories` 浏览 B 的目录）、修改审批策略、编辑和删除工作区文件、配置服务商与模型、账号和扩展，以及更新 B 上的 Pier（协议 1.13 的 `update.*`：只安装 GitHub 最新正式版中用 B 内置公钥校验过签名的更新包，客户端不能指定更新地址或安装包；远程发起的安装写入审计日志，并在 B 的窗口中提示），以及在 B 上打开终端（协议 1.18 的 `terminal.*`：shell 以 B 上运行 Pier 的用户身份运行，等同于在 B 上登录；只在 B 的桌面端中可用，属于打开它的连接，连接断开即挂断；`terminal.open` 连同目录写入审计日志，输入内容不记录）。只有决定“谁能连接 B”的操作仍仅限 B 本机：配对、设备管理、远程访问设置与 `peer.*`，相应的事件也不会发给远程连接，因此已配对的设备不能再把第三方引入 B，也不能把自己从 B 的设备列表中隐藏。“在文件管理器中显示”只作用于本机，查看其他电脑时隐藏；内置终端在工作区所在的电脑上打开（其他电脑上的 Pier 需要升级到支持终端的版本）。
- **方向**：配对是单向授权：A 能连 B 不代表 B 能连 A。两台电脑想互相连接，需要各自在对方上配对一次（且被连接的一方开启局域网访问）。A 只需要能出站连接 B，不需要开启自己的远程访问。
- **吊销与移除**：在 B 上移除 A，A 经代理的连接立即以 4403 断开，A 提示需要重新配对；在 A 上“移除”B 只删除 A 保存的记录（`peer.remove`），不影响 B 上的设备登记，要撤销访问必须在 B 上操作。
- **影响范围**：配对后 A 可以把 B 上的任意目录添加为工作区，并把审批策略设为“自动”，相当于以 B 上运行 Pier 的用户身份执行命令；只与自己信任的设备配对。A 的本地 token 或 Host 私钥泄露，除了 A 本机外，还意味着攻击者可以完全控制 A 已配对的所有电脑；在 B 上移除 A 即可切断。

## 5. 中继与 P2P

手机和电脑都没有公网 IP、也不在同一网络时，经 Pier Relay（`apps/relay`，自建）连接，并在可能时切换到点对点路径。

### 5.1 中继

- **只转发密文。** 设备经中继打开 `/v1/connect?host=<Host 公钥>`，中继通知 Host，Host 另开一条 `/v1/accept?id=<一次性 id>` 接起，中继在两条 WebSocket 之间原样转发帧。设备与 Host 之间照常运行 §4 的 Noise 握手（配对用 XX，连接用 IK），中继拿不到会话密钥，无法读取、篡改或重放内容；它能看到的只有双方的 IP、连接时间与流量大小。
- **Host 注册需要证明私钥。** Host 连接 `/v1/host` 后，中继发送一次性随机数和临时 X25519 公钥，Host 回复 `HMAC-SHA256(X25519(Host 静态私钥, 临时公钥), "pier-relay/1 register" ‖ 随机数 ‖ Host 公钥)`。中继按公钥登记 Host，因此别人无法冒用某台电脑的身份接收它的连接（即使冒用成功，设备也会因 IK 握手失败而拒绝）。
- **两种模式。** 私有模式（默认）下 Host 还必须提供访问令牌（启动参数中配置的令牌常量时间比较，或管理后台中账号创建的令牌），只有自己的电脑能用这台中继；开放模式下任何 Host 都能注册，受总数、每台连接数与带宽限制。两种模式下设备都不需要令牌：设备只能连到已注册的 Host，并且必须通过那台 Host 的配对验证。令牌保存在 Host 的 `config.json`（0600），`remote.status` 只返回是否已保存，不返回令牌本身。
- **配对。** 中继在线时配对二维码带上 `relay=<地址>`（可以没有局域网地址）。设备先尝试直连地址，1.5 秒后（或直连全部失败后）再尝试中继；配对码仍是一次性的，XX 握手仍校验 Host 公钥与二维码一致，确认框中的来源地址标注“经中继”。
- **限制。** 每个 IP 每分钟最多 120 次连接；设备在 Host 接起前最多发送 256 KiB；Host 10 秒内未接起即关闭；同一公钥的新注册顶替旧注册（4609）。中继应部署在 TLS 反向代理后（`wss://`），以免网络上的第三方看到谁在连接哪台电脑（内容本身已加密）。
- **管理后台。** 指定数据目录（`--data-dir`，Docker 镜像默认 `/data`）后，中继在自己的地址上提供网页管理后台：账号注册与登录、每个账号自己的访问令牌（`prt_` 开头），以及管理员在线修改模式与限制。第一个注册的账号自动成为管理员（并发注册时也只有一个），因此部署后应尽快注册；之后的账号按注册方式（需审核、开放或关闭）处理。密码用 scrypt 保存，访问令牌与会话 Cookie 只保存 SHA-256（数据文件 0600），令牌只在创建时显示一次。会话 Cookie 为 `HttpOnly`、`SameSite=Strict`（经 HTTPS 时加 `Secure`），修改类请求还必须带 `X-Pier-Relay: 1` 请求头（跨站请求无法在不经 CORS 预检的情况下添加，而中继不允许任何跨域请求）；页面使用带 nonce 的 CSP，并禁止被嵌入。登录与注册每个 IP 每分钟最多 20 次。删除令牌、停用或删除账号、切换到私有模式时，不再有权注册的电脑立即被断开（4601）。管理后台不接触会话内容，也不改变上面的信任关系：即使后台被攻破，攻击者也只能让电脑注册或断开，读不到也伪造不了内容。

独立端口映射（1.39）仅允许本地认证客户端创建 `127.0.0.1` TCP 监听器，不能由已配对设备在这里创建监听器；查询目标主机监听端口沿用配对的完全信任模型，只执行固定只读系统命令。映射复用配对加密 TCP 通道，每条映射独立连接，并在管理连接/目标连接断开、配对移除或 Host 退出时销毁。不扫描公网可达性、不改变防火墙、不提升权限；审计仅记录连接目标和端口，不记录端口列表或流量。

### 5.2 P2P 路径

- **能力协商。** IK 握手的消息 1 与消息 2 携带加密且认证的能力说明（`ConnectHello`）：设备声明 `caps: ["ctl"]`（理解通道内控制帧），Host 回复 `caps: ["ctl"]`；连接经中继且 Host 开启了 P2P 时，再附上 ICE 服务器（中继内置的 STUN）。旧版本发送空载荷并忽略对方的载荷，因此新旧版本互通。
- **控制帧。** 握手后，以 `\u0000` 开头的明文是控制帧（Pier 协议帧都是 JSON 对象，不会以它开头），与普通帧一样逐帧加密、按 nonce 排序，只发给声明了 `ctl` 的一方：`rtc.offer` / `rtc.answer` / `rtc.error`（WebRTC 信令）、`fin`（不再在旧路径上发送）、`close`（数据通道没有关闭码，关闭前用它传递）。
- **建立与切换。** 设备经中继连上后，在加密通道内发送 WebRTC offer，Host（`werift`）回复 answer，双方用 STUN 打洞。数据通道打开后，设备在中继上发送 `fin`，此后只在数据通道上发送；Host 读到 `fin` 后同样切换并回 `fin`，设备随即关闭中继连接。**会话密钥与 nonce 计数不变**（不重新握手）：接收方按 nonce 顺序交付两条路径上的帧，先到的帧暂存，丢失的帧在 15 秒内没有补上即断开，因此重排、重放与丢帧仍会被发现。上层的协议连接（订阅、进行中的请求、终端）不受影响。
- **信令的安全性。** offer / answer 只经过已认证的加密通道传递，其中的 DTLS 指纹因此也被认证；数据通道上传输的仍是 Noise 加密帧，DTLS 只是额外的一层。中继看不到 SDP，也就无法把数据通道引向自己。
- **失败与回退。** 打洞失败（例如对称 NAT）时连接继续使用中继，设备在 30 秒、2 分钟后各再尝试一次。P2P 路径断开时连接结束，客户端照常重连（先直连、再中继）并按 seq 恢复。关闭或修改中继会断开经中继与 P2P 的连接（4410）；关闭 P2P 开关只影响之后的连接。每台 Host 同时进行的 P2P 建立最多 8 个，30 秒内数据通道未打开即放弃。
- **审计。** 经中继的连接、配对在审计日志中带 `detail.via = "relay"`；切换到 P2P 时记录 `route` 事件；桌面设备列表显示每台在线设备的连接方式（局域网 / 中继 / P2P）。

## 6. 审计日志

Claude Code / Codex 的原生安装与更新（协议 1.32 的 `runtime.install`）也向已配对设备开放：客户端只能选择运行时，不能指定下载 URL、安装路径或执行命令。Host 从官方平台清单或 GitHub Release 获取完整原生程序，核对 SHA-256 并探测版本后才更新用户级公共命令入口并配置用户 `PATH`，Pier 和外部终端共用该安装。远程操作记录运行时名称到审计日志，并在目标电脑提示发起设备；配置与凭据不参与安装，也不会出现在进度、事件或日志里。

Host 把远程设备的操作追加写入 `~/.pier/audit.log`（JSON Lines，0600，超过 5 MiB 轮转为 `audit.log.1`）：连接 / 断开（含来源地址）、配对结果（包括错误配对码的尝试）、吊销，以及远程设备调用的会话操作（新建、打开、关闭、删除、归档、批量清理、分叉、重命名、prompt / steer / follow-up、中止、压缩、切换模型与思考等级、回答审批）和管理操作（添加 / 移除工作区与目录、修改审批策略、写入文件的路径与字节数、删除的文件或目录路径、设置默认模型、服务商登录 / 退出与自定义接口的 id、账号登录与使用令牌、安装 / 移除 / 更新 / 启停 / 删除扩展；不记录密钥）。**不记录 prompt 原文**，只记录长度与图片数量；审批记录决定（允许一次 / 本会话内允许 / 拒绝）。

## 7. 已知限制与后续工作

- **明文错误帧可被伪造。** 握手阶段的 `error` 帧没有认证，处于中间人位置的攻击者可以让手机误以为设备已被吊销或配对失败。这只影响可用性：攻击者无法借此获得访问权，手机重新配对时仍会校验 Host 公钥。
- **Host 私钥以文件形式保存**（0600）。之后可迁移到系统钥匙串（macOS Keychain / Windows DPAPI / libsecret）。
- **没有针对 IK 握手的速率限制**，只有并发上限和超时。未登记设备的握手在 Host 回复前就被拒绝，代价只是一次 X25519 运算。
- **局域网地址会变化。** 手机优先尝试上次成功的地址；地址全部失效时需要重新配对。基于 mDNS 的自动发现（手机端）留到后续版本。
- 生物识别解锁手机端与推送通知尚未实现。
- **中继可以拒绝服务。** 中继能丢弃或延迟帧、拒绝某台电脑注册，但无法读取或伪造内容；需要时换一台中继，或改用局域网 / Tailscale。
- **Host 端的 WebRTC 是纯 JS 实现（werift）**，吞吐低于原生实现（约 1 MB/s 量级），流式回复不受影响，大文件传输会比经中继慢；手机端使用原生的 react-native-webrtc。
- 首次开启远程访问时，macOS / Windows 可能弹出防火墙提示，需要允许 Pier Host 接受传入连接。
